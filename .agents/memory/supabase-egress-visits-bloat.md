---
name: Supabase egress / visits table bloat root cause
description: How we diagnosed a Free Plan egress overage and found a write-path bug causing unbounded row duplication.
---

When diagnosing Supabase Free Plan egress/storage overages, don't assume it's read traffic (polling, unbounded SELECTs) — check `pg_total_relation_size` across all tables first (`SELECT relname, pg_total_relation_size(relid) FROM pg_catalog.pg_statio_user_tables ORDER BY 2 DESC`). One table can dwarf the rest.

**Root cause found here:** the capacity-analysis upload pipeline (`geographical-extraction.ts`) extracted visit rows from an Excel upload and called `saveVisit()` (a plain INSERT) once per row on every processing run, with no delete/upsert of prior rows for the same dates first. Re-processing the same week's data repeatedly caused the same visits to be inserted again and again — one client/date/time combo had accumulated 45 duplicate rows. This grew a table to 614k rows / 257MB from what should have been ~40k rows / 14MB.

**Why:** any pipeline that re-runs over the same logical time window (daily sync, re-upload, retry) must clear or upsert the prior rows for that window before inserting, or storage/egress grows unbounded even though the *logical* dataset size is stable.

**How to apply:** before bulk-inserting rows scoped to a set of dates/keys, delete existing rows for that same scope first (see `clearVisitsForDates` in `server/repositories/geo.repository.ts`). Also watch for N+1 read patterns in the same kind of per-row processing loop (was calling `getClientLocationByName` once per row instead of batch-fetching all locations for the branch upfront).

**Unrelated but same-day finding — stale starred selections in BD-matcher PDF export (2026-08-17):** `starredMap` entries (client enquiry matcher stars) are stored independently of live match results and were never re-validated before export. If the underlying data is reprocessed and a starred CarePro loses availability on a day, the matcher grid correctly shows "No Availability" but PDF export still rendered the stale name/time, because it read the stored star blindly. Fixed with `pruneStaleStars()` in `client/src/utils/bd-matrix-utils.tsx`, applied before both PDF export call sites in `ClientEnquiryMatcher.tsx`. **Why:** any feature that persists a "selection" pointing into external data (an employee, a slot, a row) needs to re-validate that selection against current data before presenting/exporting it — persisted selections silently go stale. **How to apply:** if a similar mismatch between what the UI shows live vs. what gets exported/reported turns up elsewhere, check whether a stored selection is being trusted without revalidation against the current source data.

**Unrelated finding — BD-matcher travel time service was a leaky singleton (2026-08-19):** `travelTimeService` (server/features/travel/travel-time-service.ts) is a module-level singleton whose in-memory ORS/session cache is only meant to reset "each scheduling run", but nothing ever called `resetSourceStats()` for the client-enquiry-matcher endpoints — so it silently persisted for the entire server process lifetime across unrelated requests/branches/clients, serving old travel-time numbers (e.g. from before an employee's address was corrected) with no way to refresh except a full restart. This is also why ORS's own dashboard showed few/no calls during repeat testing — repeat coordinate pairs were served from the ancient in-memory cache instead of hitting the API. Fixed by calling `travelTimeService.resetSourceStats()` at the very start of each top-level bd-matcher controller entrypoint (bdMatch, bdMatchMultiVisit, bdMatchMultiWeek), so every user-initiated "Match" click gets live ORS data while still sharing the cache within that one run (across weeks/visits) as originally intended. **Why:** a shared/singleton cache with no natural request boundary will silently outlive its intended scope unless something explicitly resets it at that boundary. **How to apply:** if a service is described in comments as "resets each run" or "session cache", verify something actually calls the reset at the start of every run it claims to scope to — don't trust the comment.

**Update (2026-08-17):** confirmed via `pg_stat_statements` that the N+1 `getClientLocationByName` pattern above was still live — ~3.9M cumulative calls vs. ~450 actual client rows, the single largest contributor to egress found in that pass. Fixed in `geographical-extraction.ts` and all three client-visit-extraction functions in `excel-visit-extractor.ts` (`extractClientVisitsFromGHExcel`, `extractAllClientVisitsFromGHExcel`, `extractEmployeeVisitsFromGHExcel`): each now calls `getAllClientLocations(branchId)` once up front and does in-memory `Map` lookups by client name inside the row loop, instead of a DB round trip per row. This is safe because none of those functions write to `client_locations` mid-loop (writes happen only after the loop, or not at all) — so a snapshot taken at the start is equivalent to a live per-row read. Deliberately left untouched: `travel-time-service.ts`'s on-demand single-client lookup (used by enquiry matching / BD-matcher / auto-scheduler), which resolves one named client at a time interactively and is not a bulk loop — if a *new* bulk loop is added anywhere that iterates visit/client rows, check it isn't reintroducing this same per-row DB call pattern.
