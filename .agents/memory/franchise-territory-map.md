---
name: Franchise territory map approach
description: How cross-franchise map territory borders were built and verified, for anyone extending the Workforce & Client Map.
---

- Territory borders are generated from real per-franchise postcode data (Sur Group's "Territory Postcodes" spreadsheet), not council-area approximation or Voronoi tessellation (both tried and rejected — see below). Pipeline: `scripts/generate-franchise-territories.mjs` buffers every real unit postcode (from `scripts/data/territory-unit-postcodes.json`, ~65k addresses via the free ONS Postcode Directory ArcGIS FeatureServer, NOT the defunct mysociety/parlvid mirror) by 2.5km, unions per franchise, clips to only the served council areas (`scripts/data/territory-served-councils.json`). Validated at 358/360 sectors matching the spreadsheet.
- Rejected approach 1 — Voronoi from ~360 sector centroids, clipped to all of Scotland: with so few points partitioning the whole country, cells balloon into unserved regions (Highland, islands, Dumfries & Galloway) that no franchise operates in, silently painting blank areas into whichever territory's point is nearest.
- Rejected approach 2 — same Voronoi, clipped to only served councils: fixed the above, but coarse per-sector-centroid cells still produced ugly dead-straight-line artifacts, e.g. a border spiking straight across the Firth of Forth, because the served-council polygons include the water and only ~1 point per sector controls a large cell.
- Fix: use *real address density* (thousands of unit postcodes per district, not one centroid per sector) and buffer-and-dissolve instead of full-plane Voronoi, so borders only cover where people actually are and follow real settlement clusters. Buffer radius trades off fragmentation (too small → "swiss cheese" disconnected islands in sparse rural sectors) against overshoot into empty land; 2.5km was the empirical sweet spot for this dataset.
- postcodes.io's autocomplete/search silently mis-resolves compacted single-digit-outward-code + sector-digit queries (e.g. "FK1 3" → matches unrelated real district "FK13"). The ONS Postcode Directory's `pcds` field avoids this because it keeps the district/sector space, so parse sectors with a regex against that field instead of string-compacting a query.
- These lessons were only caught by the user reviewing an actual map screenshot — the sector-centroid-in-polygon validation script used throughout this work only checks *known* points, never the empty space or coastline between them, so it cannot catch full-Scotland bleed or ugly water-crossing borders on its own. Always screenshot the rendered map (with real login/data) before declaring boundary work done.
- Each Home Instead franchise's own homeinstead.co.uk page (`/<slug>/about-us/`, one exception `/scottish-borders/` has no `about-us` subpage — use the root page) has an "Areas and postcodes we cover" section listing exact postcode sectors (e.g. "EH9 3") plus a separate town/area name list — this is a reliable, official, sector-granular public source, usable for any Scotland-wide Home Instead franchise, not just SUR Group's. Full postcode-to-franchise data for all 19 Scotland franchises (10 SUR Group + 9 independent) is saved at `scripts/data/all-scotland-franchise-postcodes.json`.
- When this official per-franchise website data was compared against SUR Group's older internal "Territory Postcodes" spreadsheet, real discrepancies turned up (e.g. some G31/G32/G33 sectors listed under Glasgow North internally but under North Lanarkshire and Glasgow East on the live site) — treat the franchise's own current website as the more authoritative, up-to-date source when the two disagree, since franchise boundaries get renegotiated over time and the internal spreadsheet can go stale.
- postcodes.io ambiguity trap: compacting a "district + sector" postcode string (e.g. "FK1 3" → "FK13") can collide with a real, different, unrelated outward code (FK13 = Dollar, nowhere near FK1 = Falkirk) — the API's autocomplete/search endpoints normalize away the space and can't tell them apart. For single-digit outward codes, geocode the outward code alone via `GET /outcodes/{code}` (unambiguous, exact key lookup) instead of compacting sector digits into the query string. Only use sector-level precision (via nearby-postcode radius search filtered on the exact `outcode`+`incode` fields, or Nominatim place-name geocoding as a last resort) for the few outward codes that are genuinely split across multiple franchises in the source data.
- Real franchise/territory display names differ from the shorter internal branch `displayName` used elsewhere in the app (e.g. "Ayr" vs "South Ayrshire and Kilmarnock"). Keep this real-name mapping scoped to map/territory UI only — don't overwrite `branches.displayName`, which other views depend on.
- For any new cross-branch (multi-franchise) endpoint, mirror the single-branch `resolveBranch` access-control pattern: admins bypass, non-admins are restricted to `getUserBranches(userId)`, and requested branch IDs outside that set should be silently filtered rather than erroring (since "all franchises" is a valid request for a partial-access user).
- The working ONS Postcode Directory ArcGIS endpoint for live unit-postcode centroids is `https://services1.arcgis.com/ESMARspQHYMw9BZ9/arcgis/rest/services/Online_ONS_Postcode_Directory_Live/FeatureServer/1/query` (layer id 1, not 0) — query `PCDS LIKE '<district> %'` with `outFields=pcds,lat,long`, paginate via `resultOffset` while `exceededTransferLimit` is true (maxRecordCount 2000/page). No `doterm` field exists on this layer (it's already live-only), unlike the header comment in an earlier version of the generation script implied.
- Buffering+unioning real postcodes for all 19 Scotland franchises (~120k addresses) takes ~3.5 minutes — too slow/risky for a single shell command depending on system load. The generation script checkpoints per-territory progress to `scripts/data/.territory-progress.json` and is safely resumable/re-runnable; delete that file to force a full recompute (e.g. after changing RADIUS_KM/CIRCLE_STEPS).
- Rendered map screenshots require an authenticated session that the Screenshot tool's headless browser can't obtain (no way to pass login cookies to it). Workaround: drop a temporary static HTML page under `client/public/` that loads leaflet from local `node_modules` (CSP blocks CDN scripts/styles) and fetches the same public `/data/*.geo.json` files, screenshot that unauthenticated path, then delete the temp files.
