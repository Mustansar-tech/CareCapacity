## What this error actually means

> waiting for `form` that **has** `input[type="password"]`

This tells us:

* You **successfully clicked the portal tile**
* You are now on the **credentials step**
* BUT the username/password inputs are **not inside a `<form>` element**

So this assumption is now false for *this* screen:

```ts
page.locator('form').filter({ has: locator('input[type="password"]') })
```

That’s why it waits forever.

### This is very typical of Access / ASP.NET apps

Sometimes:

* Inputs are not wrapped in `<form>`
* Or the form exists but is replaced dynamically
* Or inputs live inside a table/div with JS submit handling

Your screenshot history already hints at this.

## The key shift you need to make

At this point, **stop trying to find the “right form”**.

Instead:

* Find the **password input directly**
* Then work *upwards* or sideways from there

Password inputs are rare. Cookie banners don’t have them. Search boxes don’t have them. So they’re the safest anchor.

## The correct selector strategy for this screen

### New rule for credentials page

* Anchor on `input[type="password"]`
* Ignore `<form>` entirely
* Scope username relative to the password field

## Drop-in fix for your login step

Replace **everything** related to `form` detection with this.

### Step 1: Wait for password input (this is the real signal)

```ts
const passwordInput = page.locator('input[type="password"]');
await passwordInput.waitFor({ state: 'visible', timeout: 30000 });
```

If this appears, you are on the credentials page. Period.

---

### Step 2: Find username input relative to it

Usually the username is the **nearest visible text input before the password**.

```ts
const usernameInput = page.locator('input[type="text"]').filter({
  hasNot: page.locator('#vendor-search-handler') // exclude cookie search if present
}).last();

await usernameInput.fill(USERNAME);
await passwordInput.fill(PASSWORD);
```

We use `.last()` because:

* Cookie/search inputs come first
* Login inputs come later in the DOM

---

### Step 3: Submit

Do **not** assume a form submit.

```ts
await page.locator('input[type="submit"], button').filter({
  hasText: /login/i
}).first().click();
```

If that selector is flaky, this fallback always works:

```ts
await passwordInput.press('Enter');
```

ASP.NET almost always wires Enter on password fields.
