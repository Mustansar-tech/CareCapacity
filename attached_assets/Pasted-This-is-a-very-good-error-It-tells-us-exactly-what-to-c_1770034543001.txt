This is a **very good error**. It tells us exactly what to change, and it’s a common Playwright mistake with legacy ASP.NET apps.

Let’s break it down calmly.

---

## What this error actually means

> `page.waitForLoadState: Timeout 30000ms exceeded`
> logs show:
>
> * `"domcontentloaded" event fired`
> * `"load" event fired`

This means:

* The page **did load**
* DOMContentLoaded **already fired**
* Load **already fired**
* But your code is still waiting for a load state that will **never happen again**

In short:
👉 you are waiting **after** the event already occurred.

So Playwright waits forever and times out.

---

## Why this happens on People Planner

People Planner is a classic ASP.NET WebForms app.

Key behaviour:

* It does **postbacks**
* It updates parts of the page
* It often **does not trigger a new navigation**
* URL may change slightly or not at all

So this pattern is **wrong** here:

```ts
await page.click(...);
await page.waitForLoadState('domcontentloaded');
```

If the click triggers a postback, not a navigation, Playwright will never see a new load event.

---

## The golden rule for this app

❌ **Do not use `waitForLoadState` after clicks**
✅ **Wait for a visible UI change instead**

This applies to:

* Client ID submit
* Portal tile click
* Login submit
* Menu navigation

---

## What to change right now (this is the fix)

### ❌ Remove this line

Wherever you have:

```ts
await page.waitForLoadState('domcontentloaded');
```

or

```ts
await page.waitForLoadState('load');
```

after a click, **delete it**.

---

## What to use instead (correct pattern)

You should always wait for **the next expected element**, not a load state.

### After portal selection, you expect the username/password form

So instead of waiting for load state, do this:

```ts
// Click portal tile
await tiles.first().click();

// Wait for login form inputs
const loginForm = page.locator('form').filter({
  has: page.locator('input[type="password"]')
});

await loginForm.waitFor({ state: 'visible', timeout: 30000 });
```

That’s it. No load state.

---

## Corrected login flow (final, stable version)

### Client ID step

```ts
await page.goto(LOGIN_URL, { waitUntil: 'domcontentloaded' });

const clientIdInput = page.locator('form input[type="text"]').first();
await clientIdInput.fill(CLIENT_ID);
await page.locator('form input[type="submit"]').click();
```

### Portal selection

```ts
const tiles = page.getByRole('link');
await tiles.first().click();
```

### Username / password page

**Do NOT wait for load state**

```ts
const loginForm = page.locator('form').filter({
  has: page.locator('input[type="password"]')
});

await loginForm.waitFor({ state: 'visible', timeout: 30000 });

await loginForm.locator('input[type="text"]').fill(USERNAME);
await loginForm.locator('input[type="password"]').fill(PASSWORD);
await loginForm.locator('input[type="submit"], button').click();
```

### Confirm login success

```ts
await page.waitForSelector('text=Dashboard', { timeout: 30000 });
```

---

## Why this works

* You stop waiting for browser lifecycle events that won’t repeat
* You wait for **business-state changes**, not technical ones
* This matches how ASP.NET apps actually behave

This one change usually fixes **all remaining login hangs** on Access products.

---

## Important mindset going forward

For the rest of People Planner automation:

* ❌ Don’t wait for load states after clicks
* ❌ Don’t rely on URL changes
* ✅ Always wait for the next meaningful UI element
* ✅ Think “what should appear next?”

Apply this same rule later when:

* Opening Reports
* Hovering menus
* Triggering exports
