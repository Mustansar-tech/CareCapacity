Care Capacity only. No live changes.

06

Layout for the task

A timetable is a workspace, not a narrow confirmation dialog. Preserve context, make explicit actions reachable and avoid sideways scrolling on ordinary forms.

Form and workspace variants

Candidate detailsAvailability / selected day
  • Standard form: approximately 480–640px, according to content.
  • Wide workspace: use available width up to roughly 1440px.
  • Wide: candidate details alongside timetable. Narrow: single column with selected-day timetable.
  • Dialog header/footer outside one vertical content scroller. Save/cancel reachable; focused controls not obscured.
  • Use embedded container size, not viewport assumptions alone.

Dense data without hidden meaning

  • Page headers identify branch and period. Label hours, status and provenance.
  • Filter bars need visible labels, clear/reset and result counts. Preserve state without leaking across branches.
  • Tables use real headers, explicit sort state, named row actions, long-name handling and aligned numbers.
  • Only genuine two-dimensional tables/maps may use contained scrolling, with keyboard access and clear navigation.
  • British English and explicit dates. Keep stored date-only values separate from display formatting.

Responsive verification matrix—not a breakpoint prescription

Test 320, 390, 768, 1024, 1280 and 1440 CSS-pixel widths, short laptop heights, 200% zoom and 400% reflow. Check long names, dense rows, visible focus, reachable actions and unclipped inputs. A 390px guide layout is not evidence that the live application passes these checks.

07

Phased adoption & release gates

Separate business-logic changes from visual refactoring. Keep the current stack; do not introduce another UI library or bulk-replace shared components.

  1. Capture the baseline

    Record real journeys and screenshots, including BI regression-only baselines. Use synthetic or redacted data in review artefacts.

  2. Approve and isolate

    Review the draft; establish an opt-in Care Capacity boundary including portals. Root/global primitives stay unchanged until consumer coverage is proven.

  3. Build and pilot patterns

    Fields, buttons, badges, toolbars, dialog variants and async states. Pilot joiner/leaver forms; leave calculations unchanged.

  4. Adopt module by module

    Dashboard and Capacity Outlook; then Workforce/BD Matrix; then Scheduling/People Planner.

  5. Release on evidence

    Pass role, keyboard, responsive, loading/error/empty, persistence and BI non-regression checks before release.

Required checks—not completed claims

  • Type-check/build and focused unit tests; no new runtime errors.
  • Create/edit/cancel/error flows; retained values and correct saved records.
  • Branch and role boundaries, including appropriate read-only access.
  • Keyboard-only use, visible focus and dialog focus management.
  • 4.5:1 normal text; 3:1 large text and required non-text contrast.
  • Target size: WCAG 2.2 minimum 24×24 CSS pixels or a documented exception; prefer larger touch controls.
  • Reflow, zoom, short heights, no clipped fields; dark mode and every control state.
  • Shared-component consumer review and screenshot comparisons. BI baseline unchanged.

Portable named tokens → scoped CSS variables and semantic aliases → accessible primitives → domain patterns → screens. DTCG-compatible format is useful where appropriate, not a reason to change the stack.

Keep the catalogue outside production navigation unless approved. New patterns need repeated use, a state inventory, responsive examples and accessibility checks. Document exceptions with an owner and reason; deprecate variants gradually. This guide is not the runtime source of truth.

Outstanding verification

  • Tokens/primitives: computed styles, contrast and interaction states.
  • Dashboard: populated, empty, error and upload journeys.
  • Capacity Outlook: real save/edit/archive, keyboard and roles.
  • Workforce/BD Matrix: maps, long names, dense rows, matching progress and failures.
  • Scheduling/People Planner: end-to-end interactions and long-running jobs.
  • Login/admin/documentation: permissions, keyboard and consistent patterns.
  • SUR BI: baseline regression checks only.

No security scan, production database audit, load test, screen-reader conformance audit or exhaustive live-session review was performed. Security, privacy, backups, monitoring and performance require separate evidence.
